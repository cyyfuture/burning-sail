# 03 质量审核体系与 Agent 编排 —— 单步循环 · 双重检验 · 质量梯度 · 大师视角

> 《V2 作战计划总纲》附属作业文件。回答四个问题：执行循环怎么跑（§1）、怎么查（§2–3）、查到什么程度算好（§4）、拿什么当参照系（§5–6）、查完怎么记账（§7）。
> **编排能力实测结论（2026-09-12）**：①ZCode 具备子代理编排能力（Agent 工具/judge 等内置代理），但按用户指令，**执行期一律不开子代理**——一切工作主会话单步完成；②独立内容检验走 **OpenCode CLI 免费模型**，已实测链路畅通：`opencode run --model opencode/nemotron-3-ultra-free "…"`（v1.18.3；可用免费档：nemotron-3-ultra-free / nemotron-3.5-lightning-free / mimo-v2.5-free）。检查者在外部模型、独立上下文运行——**与执行者不同模型、不同会话，这才是真正的独立评审**。

## 1. 单步执行-检查循环协议（Step-Check Loop）

### 1.1 状态机（每张任务卡走一遍）

```
待办 → 执行 → 自检 → 数值检验 → 内容检验 → 登记(checklog) → 下一张
              ↑______________ 任一检验不过：修复后从"自检"重跑 ______________|
```

- **自检**：执行者对照任务卡的"注意（坑）"栏逐条自查（10 秒级）。
- **数值检验**：跑该卡指定的脚本/断言；没有脚本的卡（纯设计卡）退化为"逐条对照约束清单"（W1-002 的产物）。
- **内容检验**：把产出喂给检查者提示词卡（§3），按角色卡输出"过/改（意见逐条）/重大缺陷"；**"重大缺陷"级意见未清零前禁止进入下一卡**。
- **登记**：追加 `checklog.md`；一张卡一行，不许合并补记。

### 1.2 三级检查节奏（防"做完全查不出"也防"每步查到瘫"）

| 级 | 时机 | 查什么 | 谁 |
|---|---|---|---|
| 卡级 | 每张卡完成时 | 该卡双检验 | 执行者+一次 nemotron 调用 |
| 批级 | 每 5–10 张同类卡 | 同质化/漂移抽审（分层抽样 ≥30%） | nemotron 双角色卡交叉 |
| **W 级（GATE）** | 每个 W 完成时 | §8 检查单全项+全量数值回归+两角色卡总审+**《W 过闸报告》交用户** | 主会话组织，用户批准过闸 |

### 1.3 禁令

- 禁止跳卡、合并执行、事后补 checklog；
- 禁止在内容检验未跑时口头宣称"应该没问题"；
- 禁止执行者自己给"优秀"评级（§4 的评级只由检查者角色卡或用户给出——**运动员不当裁判**）。

## 2. 数值检验体系（半自动＋全自动）

| 层 | 载体 | 覆盖 | 触发时机 |
|---|---|---|---|
| L1 内置 DoD | 各 `build_*.py` 的自检段 | 字段零缺失/schema 校验/计数/引用存在/合计校验（share=1.00±0.01 等） | 每次 builder 运行 |
| L2 阶段脚本 | `data/check_w1.py`、`check_w2.py`…（每 W 一个，一键跑本 W 全部数值断言+汇总报告） | 跨文件交叉引用/统计指标（重复率、分布、覆盖率、禁词千字频次） | 卡级被引用时 + W 级 GATE |
| L3 全量回归 | 既有 11 个数据脚本全跑 + `check_consistency.py` + `build_engine.py --check` + 面板 smoke_test | 生产资产未被污染；全链绿 | W 级 GATE + 每次部署前 |

**半自动部分**（脚本产出报告、人/模型判读）：统计抽样报告（装配 dry-run 重复率、主味分布、文风档位分布）、禁词扫描（千字频次报警非拦截）、引用健康表（悬空引用清单）。L2/L3 脚本用 pathlib+标准库（项目铁律），输出统一为"✓/✗ + 差异明细"，✗ 时退出码非零。

## 3. 内容检验体系与 Agent 编排

### 3.1 编排拓扑

```
主会话(ZCode, 执行者)                    外部独立上下文(检查者)
  │ 产出文件 ──cat──► review.sh ──► opencode run --model nemotron-3-ultra-free
  │                                        │ 评审意见(stdout)
  │◄────────────── 追加进 checklog.md ◄────┘
  └─ 不开子代理：ZCode 的 Agent 工具/judge 在 V2 执行期封存不用
```

- **调用封装**：`V2作战计划/prompts/review.sh <角色卡> <待审文件>`（内部 = `opencode run --model <模型> "$(cat prompts/<角色>.md; cat <待审文件>)"`，输出 tee 进 checklog）。
- **模型轮换**：日常评审 nemotron-3-ultra-free；W 级 GATE 用第二模型（nemotron-3.5-lightning-free 或 mimo-v2.5-free）**换模型复审**——同一段产出两个模型都挑不出"重大缺陷"才视为内容检验通过。
- **降级路径**：opencode 不可用（断网/配额）→ 提示词卡设计为自足文本，可由用户手动粘贴到任意对话模型执行；checklog 记"人工代跑"。
- **成本纪律**：卡级评审单次输入 ≤4000 字（超长切批）；免费模型优先，禁止为检查消耗付费档。

### 3.2 检查者角色卡（提示词全文，存 `prompts/`，可直接调用）

> 使用规则：调用时把角色卡全文+待审产出一起给模型；要求它**只输出 JSON**：`{"verdict":"pass|revise|major","issues":[{"where":"","what":"","why":"","fix":""}],"notes":""}`。

**卡 A·数据工程师**（数值/结构审）
> 你是一名严苛的数据工程师，负责审校一个桌面 RPG 项目的结构化内容。你会收到 JSON 或设计表。请逐项检查：①字段完整性（对照我给出的 schema 要求）；②取值域合法性（枚举/数值区间/引用是否存在）；③一致性（同一事实在不同文件中是否冲突；比例类字段合计是否达标）；④可执行性（一个不懂设计的程序员能否只凭这份数据写出消费代码）；⑤命名规范。输出只许 JSON：verdict(pass/revise/major) + issues 数组（where/what/why/fix）+ notes。不许夸奖，只找问题；没有问题就明确写"未发现"。

**卡 B·叙事设计师**（结构/可玩性审）
> 你是一名桌面 RPG 叙事设计师，精通 Save the Cat 节拍法与任务结构设计。你会收到节拍卡/任务组件。请逐项检查：①功能清晰度——每个组件是否只做一件事且做到；②结构衔接——反转与中点拍是否咬合、失败分支是否真的"失败不卡死"；③同质化——并列的变体之间是否有实质性差异（机制差异而非换皮）；④钩子强度——玩家听到这个会不会想接；⑤历史题材合理性（14–18 世纪航海世界，不得出现时代错误）。输出只许 JSON：verdict + issues(where/what/why/fix) + notes。挑剔是美德；没有问题就明确写"未发现"。

**卡 C·资深 KP**（带团实战审）
> 你是一位带团二十年的 GAME MASTER，讨厌空话，只关心"明天晚上我拿这份东西能不能直接开团"。请检查：①拿到就能用吗——有没有需要我临场补设计才跑得起来的洞；②节奏——按这份东西走，高潮前玩家会不会睡着；③信息可得性——线索是不是真的拿得到（有没有'不掷骰可得'的一路）；④安全——涉及恐怖/酷刑/奴隶制的地方有没有给 KP 脚本而不是让玩家难受；⑤工作量——备课是否 ≤30 分钟。输出只许 JSON：verdict + issues + notes。用最挑剔玩家的眼光。

**卡 D·文学编辑**（文采审）
> 你是一名苛刻的中文文学编辑，为一部航海历史题材游戏审校朗读文本。请逐句检查：①画面感——是否一句一画面，具体名词与动词是否驱动句子；②禁词——"感到/觉得/仿佛一般/无形的/莫名"等虚词是否出现；③陈词滥调——"波涛汹涌/心潮澎湃"类套话零容忍；④时代感——比喻系统是否取自航海世界（帆/缆/罗盘/账本），不得出现电学/心理学现代词汇；⑤朗读性——念出声是否顺口，长度是否适合口头表演（≤40 字/句为宜）。对每句给出：判级（合格/优秀/重写）+ 一句理由；最后给整批 verdict(pass/revise/major) 的 JSON。重写建议必须给出你的示范句。

### 3.3 双盲与仲裁

- 检查者**只见产出**，不见设计说明与自我评价（防锚定）。
- 两个检查者意见冲突：执行者可答辩一次（写入 checklog），仍冲突则标记 `🤝待用户裁决`，进 W 级 GATE 的"遗留分歧清单"——**不得私自择一**。
- 评审意见本身抽检：每 W 随机取 3 条意见让用户判"这意见有用吗"——校准检查者价值，连续无用则换模型/换卡。

## 4. 质量梯度（合格 → 优秀 → 极为优秀）

> 三级判据按产出类型分五类。**执行者只对"合格"负责；"优秀/极为优秀"由检查者与用户在 GATE 评级**——分级写进 W 过闸报告。

### 4.1 数据表 / schema

| 级 | 判据 |
|---|---|
| 合格 | schema 校验全过；字段零缺失；引用无悬空；命名符合 W1-003 正则 |
| 优秀 | + 字段 description 让弱 Agent 一次写对（试写 3 例零错）；统计指标进绿区（重复率<30%、分布达配平） |
| 极为优秀 | + 数据可反向生成文档（字典自动渲染）；edge case 有显式拒绝与提示（错误信息能指到字段）；后续 W 零 schema 变更 |

### 4.2 内容文案（节拍卡/描述句/开场白/钩子）

| 级 | 判据 |
|---|---|
| 合格 | 六件套齐；无禁词；版权标注齐；检查者卡 B/D 无"重大缺陷" |
| 优秀 | + 卡 B 判"每件可玩"、卡 D 判级 ≥80% 合格且 ≥30% 优秀；变体间有机制差异（非换皮）；文采盲评均分 ≥3.5 |
| 极为优秀 | + 用户盲评出现"想直接拿去开团"的条目 ≥10%；范例被 03 文件收为文标杆；同批次重复率 <15% |

### 4.3 代码（builder / check 脚本）

| 级 | 判据 |
|---|---|
| 合格 | 全绿；pathlib+标准库；--check 可重复运行幂等 |
| 优秀 | + 错误信息指到字段；全管线一键跑通；脚本自带 --help |
| 极为优秀 | + 新 JSON 加字段时自检规则**自动扩展**（表驱动校验）；他人零上下文可维护 |

### 4.4 文档（计划/字典/报告）

| 级 | 判据 |
|---|---|
| 合格 | 覆盖该 W 全部任务卡；引用编号有效；前后无自相矛盾 |
| 优秀 | + 弱 Agent 实测照做：抽 3 卡给独立会话执行，零追问完成 |
| 极为优秀 | + 章节可独立演读（新会话只读该卡即懂）；出现"预防了执行者没意识到的坑"的条目 |

### 4.5 工具交互（面板新页签/网格图）

| 级 | 判据 |
|---|---|
| 合格 | 功能可用；无 JS 报错；冒烟测试绿 |
| 优秀 | + KP 实操 10 分钟无卡点；打印/导出物直接可用 |
| 极为优秀 | + 用户主动说"这个每天带团都想开"；零教程上手 |

## 7. checklog 与回滚

- **checklog.md 行格式**：`| 卡号 | 完成时间 | 数值检验(脚本名:结果) | 内容检验(角色卡:verdict+要点) | 备注 |`。
- **不过闸处理**：修复→重跑该卡两检验→连续 2 轮修不过→升级为"待用户裁决"条目，跳到下一张**独立**卡（依赖链断裂时才允许停）。
- **回滚**：每个 W 开工前打 git tag（`v2-w1-start`…）；GATE 不过且短期修不完→回 tag 重来该 W，checklog 保留（教训资产）。
- **样例行**：
`| W1-020 | 09-13 10:22 | schema 校验3过1错已修/share=0.99 拒收用例通过 | 卡B:revise(占场说明补充后pass) | 首次跑通浮点容差 |`

## 8. W 级阶段检查单模板（每个 GATE 复制执行）

1. [ ] 本 W 全部任务卡 checklog 行齐（数量对字典）
2. [ ] `check_wN.py` 一键全绿（数值层汇总）
3. [ ] L3 全量回归绿（11 builder + consistency + engine --check + smoke_test）
4. [ ] 内容抽审：分层抽样 ≥30%，双模型评审均无"重大缺陷"
5. [ ] 版权扫描：quote_type 100%；技法仿写无过度重合报警
6. [ ] 禁词/文风分布报告出数
7. [ ] 对比复核（§5.2 模板）完成且产出 ≥1 条改进项
8. [ ] 五视角问题清单（§6）逐条作答并归档
9. [ ] 质量梯度评级表（§4）填毕——**评级者=检查者卡/用户，非执行者**
10. [ ] 《W 过闸报告》产出并提交用户；遗留分歧清单显式列出
11. [ ] git tag 打点（`v2-wN-gate`）
